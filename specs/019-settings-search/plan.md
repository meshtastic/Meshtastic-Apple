# Implementation Plan: Settings Search

**Branch**: `019-settings-search` | **Date**: 2026-09-13 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/019-settings-search/spec.md`

## Summary

Add a search field to Settings that finds an individual control by name, keyword or option
value, shows which screen and section it lives on, and opens that screen when tapped. The
in-app documentation is searched from the same field and returned in its own section.

Everything a proto-backed setting contributes to the index comes from the protobufs.
`label`, `description` and `keywords` join `unit`, bounds, `diy_only`, `admin_only` and
`deprecated` as `(meshtastic.field_metadata)` attributes, and the generators emit string
attributes as `String(localized:defaultValue:comment:)` keyed by the field's full proto
name. Xcode's extractor pulls those into `Localizable.xcstrings` on build, so the English
in the schema is the source string and translations live in the app's catalog. One source
of truth for what a setting is called, shared by every client.

Picker options and bitfield flags come from a second extension,
`(meshtastic.enum_value_metadata)`, on the enum values — a picker offers enum values, and a
field carries one label, so the ten toggles behind `position_flags` are named by the
`PositionFlags` values rather than by the field.

The upstream half is complete and green: [#952](https://github.com/meshtastic/protobufs/pull/952)
for the mechanism, [#1081](https://github.com/meshtastic/protobufs/pull/1081) for 155 field
and 122 enum-value annotations seeded from strings this app already carries. Getting there
turned up three latent generator bugs, all fixed with tests — see
[research.md](./research.md) D3. Nothing in this repository has changed yet.

Because the registry now carries localizable strings it must be generated into the **app
target**, not the `MeshtasticProtobufs` package: `SWIFT_EMIT_LOC_STRINGS` is per-target
and a SwiftPM package has neither it nor a catalog.

The drift guard is what keeps the index honest where the schema cannot reach: a test
parses the config protos and fails when a field is neither indexed nor exempted, alongside
a test that every entry's label still exists in the view file it claims to live in.

## Technical Context

**Language/Version**: Swift (latest stable), Swift Concurrency
**Primary Dependencies**: SwiftUI (`.searchable`, `NavigationStack`), Foundation (`localizedStandardContains`), `MeshtasticProtobufs` (generated `FieldMetadataRegistry`), the bundled docs index
**Storage**: None — the index is static, built once at launch and held in memory; no SwiftData schema changes
**Testing**: Swift Testing (`@Suite`, `@Test`, `#expect`) — index completeness against the config protos, label drift against view sources, per-screen entry counts, ranking determinism
**Target Platform**: iOS 17+, iPadOS 17+, macOS 14+ (Catalyst)
**Project Type**: Mobile app — feature addition to the existing Settings screen
**Performance Goals**: Filtering the full index per keystroke with no visible lag; index construction off the first frame
**Constraints**: Works offline and with no radio connected; no new third-party dependency; must build and search correctly when the field-metadata registry is absent
**Scale/Scope**: ~270 indexed controls across 42 settings destinations, 221 config proto fields in 29 messages, 31 documentation pages

**Structure Decision**: The index is app data, not view code, so it sits under
`Meshtastic/Model/` beside `ConfigModels.swift` — the SwiftData mirror of the same protos.
Both `Model/` and `Views/` are synced folders in `project.yml`, so new files need no
project regeneration and `xcodegen-drift.yml` stays green.

The generated registry goes in `Meshtastic/Model/` too, because its `String(localized:)`
calls are only extracted in a target that has a string catalog and `SWIFT_EMIT_LOC_STRINGS`
— see research D2. Point `--fieldmeta-swift_out` straight at that directory: this plugin
emits a bare filename with no package-path prefix.

## Sequencing

Upstream first, then three pull requests here, each its own change per the repo's
one-change-per-PR rule:

**Upstream (meshtastic/protobufs)**

- **[#952](https://github.com/meshtastic/protobufs/pull/952)** — the mechanism only: the
  `field_metadata` and `enum_value_metadata` extensions, both generators, localized string
  emission, and three generator fixes. Five worked-example annotations, no bulk data.
- **[#1081](https://github.com/meshtastic/protobufs/pull/1081)** — the annotations, based
  on #952's branch so the mechanism can be reviewed on its own. Retargets to `master` once
  #952 merges.
  Between them: 122 enum values across 13 enums and 155 fields across 24 messages, seeded
  from strings the app already carries. 37 fields are deliberately unannotated - no control at all, not yet
  offered by this client, or a label the app renders from a value - and form the
  exemption list FR-015a names. `keywords` is unseeded and can be added by hand
  where a term is genuinely absent from the label.

**This repo**

1. **String catalog migration (FR-016)** — `.localized` → `String(localized:)` across 321
   sites in `Meshtastic/Enums/`, plus `UpdateIntervalPicker.pickerLabel` becoming
   `LocalizedStringKey`. Covers the picker *option* values, which `field_metadata`
   annotates fields and so cannot reach. Independently valuable — 239 strings are
   untranslated today regardless of search — and can proceed in parallel with the
   upstream work.
2. **Field-metadata wiring** — the `gen_protos.sh` phase, the submodule bump, the
   SwiftLint exclusions and the CI checkout fix. Lands the generated registry, and
   replaces the string properties on the 13 proto-backed app enums with registry lookups
   (their ordering, icons and `protoEnumValue()` stay).
3. **Settings search** — the index, the engine, the UI and the drift tests.
